# ADR-0011: Database migration layout, least-privilege role model, and the testcontainers integration harness

**Status:** Accepted
**Date:** 2026-08-16

## Context

Every P1 backlog item is blocked on issue #33 - the P1 milestone's own priority ordering
puts it before every other P1 issue, since #35, #36, #42, #46-#48, #51-#55 and #138 all
need a real schema, a role model, and a working migration/test harness to build on.
Before this issue, `backend/src/nptc/db/` was a docstring-only stub, `backend/migrations/`
held a placeholder README, there was no Alembic configuration, no backend settings module
(`pydantic-settings` was declared but unused), and `backend/tests/` held a single
scaffolding test whose own docstring said it goes once real backend tests land.

This issue had to settle four things at once, each with a real wrong answer available:
where Alembic's configuration lives and how it resolves a script location that survives
being invoked from the repo root; how a least-privilege application role's grants are
*proven* refused rather than merely documented; how integration tests reach a real
Postgres instance without depending on a shared, stateful development database; and how
the append-only audit table's grant survives a schema round-trip instead of silently
depending on migration ordering.

## Decision

**Alembic configuration lives in the root `pyproject.toml` as `[tool.alembic]`, not in a
`backend/alembic.ini`.** Alembic 1.19 supports reading its configuration directly from
`pyproject.toml` (`Config(toml_file=...)`, and the CLI's own default file search order also
tries `pyproject.toml` before `alembic.ini`). `script_location = "%(here)s/backend/migrations"`
is the load-bearing detail: Alembic's `ScriptDirectory.from_config` resolves a *relative*
`script_location` against the process cwd, and every `uv run` command in this repo runs
from the repo root - a `backend/alembic.ini` with a relative `script_location` would break
every invocation. `%(here)s` substitutes the absolute directory of the config file itself,
so it is invariant to cwd. No `sqlalchemy.url` is committed anywhere (NFR-26); `env.py`
resolves the connection at runtime instead (below).

**`backend/migrations/env.py` resolves a database connection by exactly two routes, tried
in order:** `config.attributes["connection"]` (a live `Connection` the test harness hands
in directly - Alembic's own connection-sharing recipe), then
`MigrationSettings().migration_database_url` (the operator path, documented in
`docs/operations/upgrade.md`). `MigrationSettings` is a dedicated `pydantic-settings` class
carrying only `migration_database_url`, separate from the app-facing `DatabaseSettings`
(`nptc.settings`) which carries only `database_url` - both fields living on one combined
class would mean `env.py` demanded `NPTC_DATABASE_URL` too, a variable Alembic has no use
for at all. There is no third fallback to `config.get_main_option("sqlalchemy.url")` - a
misconfigured environment must fail loudly, naming the missing variable, rather than
silently attempting Alembic's own placeholder URL. `env.py` also guards `fileConfig()`:
with no `alembic.ini` on disk,
`config.config_file_name` is still the literal string `"alembic.ini"` (the CLI's own
default when no ini file is found), and calling `fileConfig()` on that nonexistent path
raises. This is the most likely "works in the test harness, breaks from the CLI" bug in the
whole issue, because the harness's programmatic `Config(toml_file=...)` leaves
`config_file_name` as `None` and never reaches the guard at all.

**A repo-local `backend/migrations/script.py.mako` replaces the stock template**, using
`from __future__ import annotations`, `collections.abc.Sequence`, and `str | None` instead
of `typing.Sequence`/`typing.Union`. `import sqlalchemy as sa` stays unconditional, matching
the stock template: autogenerate's rendering assumes `sa` is available and does not add it
to the dynamic `imports` block itself, so removing it breaks any autogenerated migration
that actually uses `sa.Column(...)` (confirmed empirically - `ruff check` failed on
`F821: Undefined name 'sa'` in the audit_event migration until this import was restored). A
hand-written, autogenerate-free migration that ends up not using `sa` (like `0001`, written
directly rather than templated) simply doesn't carry the import in the first place.

`[[tool.alembic.post_write_hooks]]` runs `ruff check --fix` then `ruff format` against every
newly generated revision, using hook `type = "module"` (`python -m ruff ...`), not the more
common `console_scripts` - ruff ships as a binary wheel and registers no `console_scripts`
entry point for `importlib.metadata` to discover (confirmed empirically: `console_scripts`
failed with "Could not find entrypoint console_scripts.ruff").

**A minimal `audit_event` table lands here**, with its `INSERT`/`SELECT`-only grant and the
refusal tests proving it. The hash chain (`prev_hash`/`entry_hash`, NFR-10) stays with #36;
the `TRUNCATE` re-assertion after a downgrade/upgrade round-trip stays with #35 (this issue
proves it once, directly, not merely re-asserts it). **Identity, not `serial`**: an identity
column's backing sequence is an internal dependency of the column and is not ACL-checked
against the inserting role, so `INSERT` on the table alone suffices; a `serial` default is a
plain `nextval(...)` evaluated with the *inserting* role's own privileges and would need a
separate `GRANT USAGE ON SEQUENCE` - the classic thing forgotten on a re-migration. This was
proven empirically (`backend/tests/test_db_audit_privileges.py`), not assumed. The grant
lives in the **same migration that creates the table** (`0002_audit_event.py`), not a later
"permissions" migration - table ACLs (`pg_class.relacl`) are cluster state that lives and
dies with the table itself, so a separate migration would leave the re-created table
grant-less after a `downgrade base` → `upgrade head` round-trip - exactly the shape issue #35's
re-assertion criterion exists to catch.

**`nptc.db.roles`** holds the app role name and every grant/revoke statement as plain string
constants (never an f-string, `%`/`+` concatenation, or `.format()`), imported by both the
migration and the tests, so the granted and asserted privilege sets cannot drift apart.
`GRANT ALL` is never written against an audit table; the `REVOKE UPDATE, DELETE, TRUNCATE`
statement is belt-and-braces (nothing was granted them), but it is the literal string
`backend/tests/test_sql_parameterisation.py`'s NFR-22 guard greps for.

**The NFR-22 guard (`test_sql_parameterisation.py`) treats "argument 0 of an execute call
must not be built from runtime data" as the actual rule** - not "argument 0 must be an
`ast.Constant` node" read literally. A `Name`/`Attribute` reference to a module-level
constant (`roles.GRANT_AUDIT_EVENT_SQL`) passes; an f-string, `%`/`+` concatenation, or a
`.format()` call at the call site fails, and so does an f-string assigned to a variable
above the call (rule 2) or a literal `GRANT ALL` against `audit_event` anywhere (rule 3).
The distinction that actually matters for SQL injection is whether runtime data reaches the
query text, not whether the reference is spelled inline - and rejecting `Name`/`Attribute`
references would make `nptc.db.roles`'s entire reuse-across-migration-and-test design
impossible to write without duplicating every SQL string. The guard ships with its own
positive control run over an inline source string, so a refactor that silently made the
walker match nothing would fail loudly rather than the check rotting into one that always
passes.

**testcontainers runs the tag `deploy/compose.yml` pins** (`postgres:18.4` today), parsed at
runtime by `backend/tests/conftest.py`'s `_image_from_compose()` so there is exactly one
pin; bumping compose moves the integration test target automatically. The PRD's "Postgres
16" is the documented floor (ADR-0001), not the test target. `driver="psycopg"` is
required - testcontainers 4.x defaults to `psycopg2`, which is not a workspace dependency.
Migrations are applied via `command.upgrade`, never `metadata.create_all` - the acceptance
criteria are about the migrations themselves running, and `create_all` would never execute
their `GRANT`/`REVOKE` statements at all. The restricted connection
(`nptc_app_login`) is a genuinely separate authentication, not `SET ROLE` on the owner
connection - a superuser's `SET ROLE` still bypasses some privilege checks, so only a real
non-superuser login proves the grant. Each refusal (`UPDATE`, `DELETE`, `TRUNCATE`) gets its
own test function: a privilege error aborts the surrounding transaction, so a second
statement in the same transaction would fail with `25P02` and mask the assertion under test.

**No skip-when-Docker-absent logic, and no `_no_real_network` autouse guard in
`backend/tests`.** Docker is already a declared prerequisite (`CONTRIBUTING.md`); the new
fact to document is that `uv run pytest` now needs it *running*, not merely installed. The
`_no_real_network` guard used by `transform/tests` and `shared/tests` is directory-scoped
and does not reach `backend/tests` - and could not, since testcontainers must open a real
TCP socket to the mapped container port. NFR-37 is proven for this tree instead by the
`backend-integration` CI job blocking all *other* egress (`.github/workflows/ci.yml`):
`docker pull` the pinned tag before blocking, `TESTCONTAINERS_RYUK_DISABLED=true` to avoid a
second, post-block image pull for the Ryuk reaper (an ephemeral CI runner is discarded
either way, so Ryuk's crash-cleanup role buys nothing there - do not set this flag for local
development, where a long-lived machine still wants it), then the same `iptables` rules
`transform-offline` uses. This proves the *test process* makes no other egress, not that the
container makes none - container traffic transits `FORWARD`, not `OUTPUT`, and `-P FORWARD
DROP` is deliberately not added on top, since it risks breaking the bridge networking the
container itself needs for no NFR-37 gain. Adding `scripts/tests` to this job's run means
every one of `testpaths`' four directories has now run under an egress block at least once
(between this job and `transform-offline`), which is what actually justifies moving NFR-37
to `implemented`.

**The downgrade/upgrade round-trip is checked with a reflection fingerprint, not
`compare_metadata` alone**, and it runs against its own dedicated `nptc_roundtrip` database
in the same container rather than the shared `nptc_test` database:
`downgrade base` drops every table, and sharing a database with the session-scoped
`app_engine`/`owner_engine` fixtures would produce intermittent `UndefinedTable` errors from
pooled connections still open against the dropped schema. `compare_metadata` only asks "do
the migrations match the models?" - it is blind to extensions and grants, and a
downgrade/upgrade pair broken identically in both directions would still compare clean. The
fingerprint instead covers `inspect()` over columns/PK/FKs/uniques/checks/indexes, plus
`pg_extension`, plus `information_schema.role_table_grants` - the last of which is what
makes this single test also satisfy #35's "grants re-asserted after downgrade then upgrade"
criterion, nearly free here and expensive to retrofit later. Incidentally, this test is a
live proof that `0001`'s `IF NOT EXISTS` role guard is load-bearing: `nptc_app` already
exists in the cluster (created against `nptc_test` first) by the time the dedicated
database's own migration creates it again, since roles are cluster-wide, not per-database.

**`downgrade()` in `0001` drops both extensions but deliberately does not `DROP ROLE`**:
that errors if the role holds privileges in any database in the cluster, which would make
`downgrade base` fail on a shared cluster. A role is not schema, so the round-trip
criterion still holds without it; the asymmetry is stated explicitly in
`docs/operations/upgrade.md` rather than left for a future reader to puzzle over.

**NFR-39 moves to `implemented`; NFR-37 moves to `implemented` with its `evidence:`
repointed at the new CI job; NFR-22 stays `in-progress`.** The NFR-22 guard is real and
enforced from this point on, but the half of NFR-22 actually carrying risk (FR-13's JSONB
filtering against registry-validated keys) has no code, no registry (#51), and no search
(#138) yet - marking it `implemented` on the strength of a scanner running over an
otherwise-empty codebase is exactly what the register's evidence/status distinction exists
to prevent (ADR-0002; NFR-25/NFR-26 are existing precedent for the same restraint).

## Rejected alternatives

| Alternative | Why not |
|---|---|
| `metadata.create_all` in the test fixtures, instead of running real migrations | Never executes the `GRANT`/`REVOKE` statements the acceptance criteria are actually about, and diverges from what a real deployment does the moment a second migration lands. |
| SQLite in-memory for backend tests | Explicitly excluded by NFR-39; also cannot express Postgres-specific behaviour this issue depends on (extensions, role-level GRANT/REVOKE, `INET`/`JSONB`/identity columns). |
| A `BEFORE UPDATE OR DELETE` trigger or `RULE` for append-only, instead of a privilege grant | PRD Section 14.1 bans business logic in database triggers/functions, and either mechanism is bypassable by the table owner - a missing privilege is not. |
| Row-level security instead of a table-level GRANT/REVOKE | Does not restrict `TRUNCATE`, and is bypassable by the table owner in the same way a trigger is. |
| A `LOGIN` app role with a password embedded in the migration | Violates NFR-26 outright; the migration only ever creates a `NOLOGIN` role, and `LOGIN` role provisioning is an out-of-band operator step (`docs/operations/upgrade.md`), reproduced only inside the disposable test container by `conftest.py`. |
| `ALTER DEFAULT PRIVILEGES` instead of a per-table `GRANT` | Solves a different problem (privileges on *future* tables created by a given role) and would obscure exactly which privileges the audit table carries, which the refusal tests need to assert against something concrete. |
| `alembic.ini` in `backend/` or at the repo root | Breaks `script_location` resolution from the repo root (the load-bearing detail above), and duplicates configuration ownership that the root `pyproject.toml` already holds for every other tool. |
| `pytest.mark.skipif` when Docker is absent | Docker is already a declared, non-optional prerequisite (`CONTRIBUTING.md`); a skip would let a broken or absent Docker daemon read as "tests passed" instead of "tests didn't run". |
| `pg_dump --schema-only` text diff for the round-trip check | Needs a `pg_dump` binary matching the server version - absent on a Windows development machine, and version-skewed against PG18 on many Linux boxes. Reflection is pure SQLAlchemy and produces a diff pytest can render directly. |
| One combined `Settings` class with both `database_url` and `migration_database_url` required | Caught in review: `env.py` instantiating that class to read `migration_database_url` would then also demand `NPTC_DATABASE_URL`, a variable Alembic never uses - an operator following `upgrade.md`'s "exactly one environment variable" claim would hit a `ValidationError` naming the wrong field. Split into `DatabaseSettings`/`MigrationSettings`, each carrying only the one field its own consumer needs. |
| The `migrated` fixture as `autouse=True` | Caught in review: every test under `backend/tests` started Docker regardless of whether it touched a database, including `test_settings.py` and `test_sql_parameterisation.py`, whose own docstrings say they need neither. Made non-autouse; `db`/`app_engine` request it explicitly, and `test_db_round_trip.py`'s `roundtrip_engine` fixture requests it too, purely to keep the "0001's `IF NOT EXISTS` guard is proven" comment true regardless of test collection order. |

## Consequences

- Every later backend issue that touches the database (#35, #36, #42, #46-#48, #51-#55,
  #138) builds on this migration layout, role model, and test harness rather than
  reinventing any part of it.
- `nptc.db.roles` becomes the one place a future least-privilege role's grants are defined -
  the pattern (constants imported by both a migration and its tests) is meant to repeat, not
  be special-cased to `nptc_app`.
- The `backend-integration` CI job runs `backend/tests` a second time (the `python` job
  already ran it, with network, for the coverage gate) - roughly 90 extra seconds of CI time,
  the same trade-off `transform-offline` already makes for `transform/tests`/`shared/tests`.
- `docs/architecture/data-model.md` and `docs/operations/upgrade.md` exist from this point
  on as the canonical references for the schema baseline and the migration/role-provisioning
  procedure, respectively - see their own documents for detail this ADR does not repeat.
