# ADR-0017: Audit hash chain construction

**Status:** Accepted
**Date:** 2026-08-17

## Context

Issue #33 shipped `audit_event` with the *privilege* half of append-only: `GRANT SELECT,
INSERT` to `nptc_app`, `REVOKE UPDATE, DELETE, TRUNCATE`, proven by refusal tests on a
fresh database (`test_db_audit_privileges.py`) and again after a `downgrade base` ->
`upgrade head` round-trip (`test_db_round_trip.py`, issue #35). That protects against the
*application* rewriting history. It does nothing against anyone holding the table owner's
credentials directly - a DBA, a restored backup, a compromised operator. Hazard H-06
("silent content change") read "privilege half implemented … not yet a real write path or
the hash chain" until this issue.

**NFR-10 (SHOULD)** is the requirement: each entry includes a SHA-256 hash over its own
content plus the previous entry's hash, forming a chain. This makes an out-of-band
`UPDATE`, `DELETE` or row re-order *detectable*, even though - holding table-owner
credentials - it cannot be *prevented*.

**Scope**, confirmed with the maintainer: the `prev_hash`/`entry_hash` columns, the digest
construction, the append writer, and a library-level `verify_chain()` the tests drive
directly, plus one real caller (`close_account` emits `user.closed`, so the chain is
exercised by production code, not only by tests). `scripts/verify_audit_chain.py` - the
operator CLI with stable exit codes wrapping `verify_chain()` - stays with **#38**;
NFR-38.5 is therefore only half-satisfied here and NFR-38 stays `planned`.

## Decision

**Two new columns, `NOT NULL` with no server default.** `prev_hash` is the predecessor's
`entry_hash` (`GENESIS_HASH`, 64 `0`s, for the first row); `entry_hash` is this row's own
digest, `UNIQUE`. There is no way to invent a hash for a pre-existing row, so
`0004_audit_event_hash_chain.py`'s `op.add_column` calls are only ever valid against an
empty `audit_event` - honest rather than awkward, given no write path has ever run
pre-alpha (`docs/operations/upgrade.md` records the constraint explicitly for a future
operator). `entry_hash`'s `UNIQUE` constraint is what makes the chain a path rather than a
DAG, and makes a replayed row structurally impossible.

**Canonical JSON, not a hand-joined string.** The digest is computed over
`json.dumps(fields, sort_keys=True, separators=(",", ":"), ensure_ascii=False)` encoded as
UTF-8 - the same idiom `transform/src/nptc_transform/report_writer.py` already uses for a
byte-identical canonical form. A JSON object is self-delimiting, so `("ab", "c")` cannot
collide with `("a", "bc")` the way naive string concatenation could. Per-type
normalisation converts a `UUID`/`ipaddress` value to its string form and a `datetime` to
UTC with a fixed 6-digit microsecond field (so the same instant hashes identically
regardless of the timezone attached to it in memory).

**The digest covers every column except two, and the exclusion is explicit and tested.**
`entry_hash` is excluded because it is the digest itself. `sequence` is excluded because
it is `GENERATED ALWAYS AS IDENTITY` - its value is unknowable before the `INSERT` and so
cannot be folded into that row's own digest. Ordering is still tamper-evident without it:
verification walks rows in `sequence` order and each row's `prev_hash` must equal its
predecessor's `entry_hash`, so a deleted or reordered row breaks the chain regardless.
`test_audit_hashing.py::test_digest_covers_every_meaningful_column` derives the expected
field set from `AuditEvent.__table__.columns` minus `{entry_hash, sequence}`, rather than
a hand-maintained list a future column could silently fall outside of.

**`GENERATED ALWAYS AS IDENTITY`, not `GENERATED BY DEFAULT`, kept as-is.** Switching to
`BY DEFAULT` would let `sequence` be folded into the digest before insert, but would
reintroduce the separate `GRANT USAGE ON SEQUENCE` issue #33 deliberately designed away
(see `nptc.db.models.audit`'s own comment) and would let a caller override the value -
exactly the kind of gap this issue exists to close, not reopen.

**`pg_advisory_xact_lock` serialises appends, not a `SELECT ... FOR UPDATE` on the tail
row.** Two concurrent appenders reading the same tail and forking the chain is the
principal failure mode here. An advisory lock needs no grant (it is role-agnostic) and is
transaction-scoped, releasing automatically on commit or rollback - and it is not a
trigger or stored function, so PRD Section 14.1's ban on business logic in the database is
untouched. `test_audit_chain.py::test_concurrent_append_serialises_through_the_advisory_lock`
proves it: connection B, given a short `lock_timeout`, is refused rather than reading a
stale tail.

**Write-time self-check: recompute and compare immediately after `INSERT`.** A JSONB
round-trip divergence (a number literal Postgres normalises, e.g. `1e2` -> `100.0`) would
otherwise surface as an unexplained chain break months later instead of a loud failure at
the point of the write. `nptc.audit.writer.AuditChainWriteError` is raised the moment this
happens, never silently swallowed.

**`verify_chain()` reports the first break and stops**, because that is the location an
operator needs - re-confirming every subsequent row as also "broken" once the first
divergence is found adds nothing. It deliberately does **not** assert `sequence`
contiguity (a rolled-back transaction legitimately burns an identity value) or
`occurred_at` monotonicity (`clock_timestamp()` can step backwards across a clock
adjustment) - both are documented in its own docstring so a future reader does not mistake
either for an oversight.

**`close_account` is the one real caller landed with this issue.** It emits `user.closed`
with the status transition, but deliberately *not* a field-level `before`/`after` diff of
the three pseudonymised columns: `audit_event` is INSERT/SELECT-only for the app role
(NFR-09) and rows are never updated or deleted, so anything written into `before` is
permanent. Writing the real pre-closure `username`/`display_name`/`organisation` values
into `before` would defeat NFR-17's pseudonymisation the moment the event recording that
pseudonymisation is itself emitted (NFR-16, PRD OI-15). `before` instead records only the
pre-closure `status` and the *names* of the fields being pseudonymised; `after` never
carries the identifying values either, only that they are now null. The idempotent
early-return path emits nothing, which is correct: nothing changed.

## Rejected alternatives

| Alternative | Why not |
|---|---|
| `GENERATED BY DEFAULT AS IDENTITY` for `sequence`, folded into the digest | Reintroduces the `GRANT USAGE ON SEQUENCE` issue #33 removed, and lets a caller override the value - both are exactly the class of gap this issue closes. |
| Hand-joined string concatenation for the digest payload, instead of canonical JSON | A JSON object is self-delimiting; a joined string is not, and risks a collision like `("ab","c")` vs `("a","bc")` that canonical JSON structurally rules out. |
| `SELECT ... FOR UPDATE` on the tail row to serialise appends | Requires a real row to lock (fails on an empty table, the very first append) and ties serialisation to table content rather than to the operation itself; an advisory lock has no such dependency and needs no grant. |
| A hand-maintained list of digest-covered columns | Drifts silently the moment a column is added without updating the list. Deriving the field set from `AuditEvent.__table__.columns` minus an explicit, tested exclusion set makes a future column's fate a deliberate choice, not an accident. |
| Verifying `sequence` contiguity or `occurred_at` monotonicity | Both are legitimate, expected properties of normal operation (a rolled-back transaction burns an identity value; `clock_timestamp()` can step backwards) - asserting either would produce false positives unrelated to tampering. |
| Building `scripts/verify_audit_chain.py` in this issue | Out of scope per the maintainer's explicit split; #38 owns the operator-facing CLI, stable exit codes and runbook wrapping `verify_chain()`. |

## Consequences

- NFR-09 and NFR-10 move to `implemented`. NFR-08 moves to `in-progress`: one real emit
  site (`close_account`) exists, not yet every state-changing write path.
- NFR-38's notes gain this issue's detection half; the CLI half (NFR-38.5) stays owed to
  #38, which is the next consumer of `verify_chain()`.
- Hazard H-06 moves from "privilege half implemented … not yet … the hash chain" to
  reflect that the hash chain itself now exists and is exercised by real production code.
- **Known limit, stated plainly here rather than left implicit**: an attacker holding
  table-owner credentials can recompute the entire chain from the point of edit forward -
  an unanchored chain detects casual tampering, not a determined rewrite. External
  anchoring (periodic off-box publication of the head hash) is the mitigation for that, and
  is out of scope for both this issue and #38.
- **A distinct, currently-undetectable gap: tail truncation.** Deleting the most recent N
  rows off the end of the chain (rather than editing a row in the middle) leaves a table
  that still verifies `ok=True` - `verify_chain` walks forward from genesis and, once the
  truncation point is reached, there is simply nothing left to detect a break against. This
  is cheaper for an attacker than the "recompute forward from an edit" limit above and a
  different failure mode from it, not a restatement of it. It is directly relevant to #38:
  an operator command built purely on `verify_chain()` walking the table forward cannot
  catch this either, so that design needs an externally-anchored expectation of the current
  head - an expected head hash plus record count, stored somewhere `verify_chain` itself
  cannot reach - to have any chance of catching a truncation.
- Once NFR-08 is satisfied for every state-changing write (not just `close_account`), every
  such write transaction will serialise platform-wide on the one `pg_advisory_xact_lock`
  (`AUDIT_APPEND_LOCK_KEY`), held until commit. That is inherent to per-row hash chaining
  with a database-side tail read - there is exactly one tail, so there can only be one
  appender at a time - and is acceptable at this platform's expected write volume, but is
  worth having on record here for whoever hits it under load later (issue #46+).
- Forward-looking caveat, out of scope for this issue: `before`/`after` payloads are
  free-form JSONB, and neither `nptc.audit.hashing` nor `nptc.audit.writer` sanitise their
  content for embedded NUL bytes (`nptc_shared.text`'s own concern, not replicated here).
  `close_account` - the one caller landed with this issue - only ever puts `status` and
  fixed field-name strings into `before`/`after`, so this cannot occur today; it becomes
  relevant only once a future caller puts real catalogue content through this path.
- #38 builds directly on this ADR's `verify_chain()` and `ChainVerification` shape; a
  future issue adding external anchoring builds on the "known limit" paragraph above.
