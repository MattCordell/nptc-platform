# Alembic migrations

Landed with issue #33 (P1-1, DB foundation) - see
[`docs/architecture/data-model.md`](../../docs/architecture/data-model.md) for the schema
itself, [`docs/operations/upgrade.md`](../../docs/operations/upgrade.md) for running
migrations and provisioning the app role's login, and ADR-0011 for the reasoning behind
the decisions below.

Alembic's own configuration is `[tool.alembic]` in the **root** `pyproject.toml`, not an
`alembic.ini` in this directory - a relative `script_location` in an ini file here would
resolve against the process's working directory, which breaks every `uv run alembic ...`
command (they all run from the repo root). Run every Alembic command from the repository
root:

```powershell
uv run alembic upgrade head
uv run alembic revision --autogenerate -m "add a thing"
```

`env.py` resolves the database connection two ways, in order: a live connection the test
harness hands in directly (`config.attributes["connection"]`), or
`NPTC_MIGRATION_DATABASE_URL` (`nptc.settings.Settings`) otherwise. There is no fallback to
a hard-coded or `alembic.ini`-configured URL - a misconfigured environment fails loudly,
naming the missing variable.

`script.py.mako` is a repo-local revision template (modern typing syntax, no unused
imports on a hand-written migration) with `ruff check --fix` and `ruff format` wired up as
post-write hooks, so a freshly generated revision is already clean.

`versions/0001_extensions_and_app_role.py` is hand-written (installs `pg_trgm`/`unaccent`,
creates the `nptc_app` role); `versions/0002_audit_event.py` is autogenerated from
`nptc.db.models.audit.AuditEvent` with its privilege grant hand-added afterwards. Both are
covered by `backend/tests/test_db_migrations.py`, `test_db_round_trip.py` and
`test_db_audit_privileges.py`, which run against a real, containerized Postgres
(testcontainers, NFR-39) - never `metadata.create_all`.
